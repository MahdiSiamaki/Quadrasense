# Backlog — suggested, not built

**Status:** living document, started 2026-10-20 at the product owner's request. Improvements that
were suggested and deliberately not built yet - for tokens, priority, or a decision still to be
made - so they are not lost between sessions. Each says what it is, the evidence behind it, the
rough cost, and what it waits on. When one is built, remove it here and name the commit.

Items that exist only because of the laptop are in `docs/operations/dedicated-hardware.md`, not
here.

`docs/research/2026-10-feature-research.md` (2026-10-21) lists some forty further candidates - new
features and improvements, with international references - awaiting the owner's choice. An item
moves here once it is chosen or deferred with a reason.

Collected on 2026-10-20 from this session and from the "not built" and "known limitations" sections
of `docs/`. Suggestions made in earlier sessions and never written into `docs/` may be missing.

## Import formats and file dates (ADR-025, 2026-11-11)

| What | Why, and the evidence | Cost | Waits on |
|---|---|---|---|
| **A RAR's dictionary read before it is unpacked** | Unpacking a RAR allocates the dictionary it was made with: 32 MB by default, 71 MiB in all for both real files measured. An archive made with a 1 GB dictionary needs 1 GB inside an API container allowed 1.5. The allocation is guarded and refused in words, **and that path has never run**: making such an archive needs several gigabytes of memory, and the attempt on the laptop filled its disk | Small: the size is in the RAR 5 file header, a few dozen lines and a fixture, refused before any allocation | Such an archive to test with; nobody has sent one |
| **RAR 4 proven** | The reader supports it and no test does: WinRAR 7 no longer writes it and none was to hand (`Fixtures/Archives/README.md`) | One fixture and its assertions | A RAR 4 archive |
| **7z, tar, xz, bzip2, Zstandard unpacked** | They are recognised by their first bytes and refused by name. The owner asked for CSV, RAR and ZIP; GSMA sends RAR | Medium: SharpCompress reads 7z and tar, but each is a reader to measure, limit and test as RAR was; 7z needs the whole archive on disk and its own dictionary | A sender who uses one |
| **A gzip made of several joined together** | It is refused as damaged: the check compares what came out with the length and CRC-32 at the gzip's end, which describe only its last part. Chosen over the alternative, which is importing a gzip cut short as a short day - the runtime's reader does not say when it stops early | Medium: a gzip reader that reports where each part ends | Such a file; `gzip`, `pigz` and the carry script make one part |
| **A date given before the upload instead of after** | A file whose name has no date is uploaded, stored, and then asked about; the page says so at the start. A date field beside the drop zone would take it first | Small: the upload already accepts a date in code (`--import-file --date`), the page does not send one | Whether asking afterwards turns out to be a nuisance |
| **Overruling a date a name says plainly** | A misnamed file has to be renamed and sent again: a typed date is refused where the name says another, so that the record shows the correction as a name and not as a keystroke | Small | The owner's decision; no misnamed file has arrived |
| **Unpacking by the worker** | It is done in the request: 2.2 s to 6.4 s for the largest daily file. At those rates a 10 GB file would be 40 s to 2 minutes, inside the proxy's fifteen | Medium: a job kind or a second queue, and an answer that arrives later than the upload | Files of several gigabytes arriving packed; the dump is loaded from the shell |
